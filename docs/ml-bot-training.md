# ML bot policy v7 training

The active v7 campaign and selection state are recorded in
[`ml-bot-policy-v7-selection.md`](ml-bot-policy-v7-selection.md). The deployed
v5 incumbent remains documented separately in
[`ml-bot-policy-v5-selection.md`](ml-bot-policy-v5-selection.md).

The Website owns the schema-v7 observation/action contract, deterministic
Boneyard training environment, PyTorch trainer, evaluation artifacts, and
compact runtime checkpoint. The server-only GameHost worker consumes the
selected artifact for summoned policy participants; checkpoints remain
separate from browser assets.

## Contract

- Observation width: 3,026 ordered float32 values.
- Action order: movement (9), target (9), ability (22), aim (9).
- Autoregressive legality: target selects an ability-mask row; ability selects
  an aim-mask row. Masks encode legality only.
- Choice/equipped descriptors: 138 values per skill.
- Observation, model, main trajectory, and choice trajectory versions: 7.
- Runtime checkpoint: compact `SDMLV7` binary. Versions 1–6 have no shim.
- Network: two tanh trunk layers, 3,026 → 512 → 256; four policy heads and
  value; 394 → 128 option scorer and separate choice value.

The final 1,242 observation values are nine ordered semantic rows: the current
primary followed by quickbar slots 1–8. Each row uses the same descriptor as a
skill offer and carries 16 exact skill-id bits, 16 exact Weld-build bits,
permanent/effective rank, family/category, every authored numeric mechanic,
and presence masks. Empty
slots are all-zero rows. This lets the chooser compare an offer with the actual
loadout and lets the combat policy learn different use patterns for
non-elemental spells that schema v5 could not identify exactly.

The primary curriculum is generated from the same authoritative native owners:
category-1 catalog rows produce the five pure primaries and
`NATIVE_WELD_BUILDS` produces all ten Welds. Consecutive seeds rotate all 15
rows. Adding a primary through those native owners automatically admits it to
collection and evaluation; the fixed uint16 identity fields remain exact after
the smooth scaled feature saturates.

The ordered contract is generated by
`frontend/tools/generate-ml-bot-policy-spec.mjs` into
`frontend/src/game/core-server/ml-bot-policy/policy-spec-v7.json`. Python loads
that artifact directly before constructing a model or taking a gradient step.

The policy amendment currently describes 60 `NATIVE_SECONDARY_ACTOR_KINDS`;
the live Website union contains 58. The checked exhaustiveness map follows all
58 live members and fails whenever the simulation adds one. No placeholder
actor kinds are added merely to satisfy the stale document count.

## Bootstrap and training

The bootstrap collects real authoritative web states across all 15 primary
loadouts and labels them with the
TypeScript semantic expert. It caps uninteresting opening rows and fails if
the dataset does not cover multiple movement, target, and ability actions.
Behavior cloning uses square-root inverse-frequency weights independently for
each action head so rare legal expert actions are not erased by the dominant
null classes. Bootstrap acceptance additionally requires at least eight expert
potion rows, at least 70% deterministic potion-action imitation over them, and
at least one direct primary-action label for every curriculum row.
Headless resets skip the presentation-only entrance sequence by placing every
participant at a collision-safe point around Solomon's encounter anchor inside
the production combat bounds, retaining the production arena transition, and
then starting the production wave director. The outside entrance spawn is
never part of a training or evaluation episode.

```sh
python tools/train_bot_policy.py bootstrap \
  --output runtime/ml-training/web-v7 \
  --samples 15000 \
  --bootstrap-epochs 30 \
  --worlds 15 --workers 8 --action-repeat 10
```

Start PPO from the resulting checkpoint. Every run requires an experiment
change, expected metric, and evaluation condition; they are appended to
`experiments.md` before collection.

```sh
python tools/train_bot_policy.py train \
  --checkpoint runtime/ml-training/web-v7/bootstrap-v7.sdml \
  --output runtime/ml-training/web-v7 \
  --iterations 10 --rollout-steps 512 \
  --worlds 15 --workers 8 --action-repeat 10 \
  --gamma 0.995 --learning-rate 0.0001 --target-kl 0.02 \
  --experiment "Schema-v7 PPO with semantic equipped loadout" \
  --expected-metric "holdout wave depth increases" \
  --eval-condition "frozen train-dist and holdout seeds"
```

Main rewards remain raw and frozen. A running standard deviation of discounted
returns scales rewards before tick-aware GAE. Each decision uses
`gamma ** executed_ticks`; an action repeat stops on the first terminal tick.
The approved gamma values are 0.99, 0.995, 0.997, and 0.999.

Run the same registered short campaign at every approved horizon with:

```sh
python tools/train_bot_policy.py gamma-sweep \
  --checkpoint runtime/ml-training/web-v7/bootstrap-v7.sdml \
  --output runtime/ml-training/web-v7/gamma-sweep \
  --gammas 0.99,0.995,0.997,0.999 \
  [the shared training arguments]
```

Before enabling learned choices, warm-start the option scorer from real skill
offers resolved by the authoritative scripted expert. Only
`choice_hidden`/`choice_score` are updated; the trunk, four combat heads, both
value heads, and every other tensor must remain byte-identical. Collection and
bootstrap fail closed on weak offer diversity or less than 95% training / 85%
holdout imitation.

```sh
python tools/train_bot_policy.py bootstrap-choices \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --output runtime/ml-training/web-v7/learned-choice \
  --samples 512 --epochs 40 --batch-size 64 \
  --worlds 30 --workers 10 --action-repeat 10
```

The resulting checkpoint is marked `choicePolicyMode=learned`. A level-up then
pauses the headless action lane, exposes the exact observation, variable option
rows, option IDs, generation, and legality mask through the strict
`solomon-dark-ml-rollout-v7-choice1` bridge, and accepts the sampled option with
its old log probability and choice value without advancing simulation time.
The interval closes at the next learned choice or terminal state. Only those
`choiceMode=learned`, `trainable=true` intervals enter SMDP PPO; scripted
incumbents remain scripted during frozen evaluation. The live GameHost follows
the same checkpoint gate and dispatches the learned result through the ordinary
player skill-selection intent.

Choice SMDP PPO updates only `choice_hidden`, `choice_score`, and
`choice_value`. The shared observation trunk is owned exclusively by the main
PPO optimizer. Do not place the trunk in both Adam optimizers: independent
optimizer moments over the same tensors caused deterministic aim-lead and
potion-probe regressions immediately after accumulated choice batches. Trainer
state records `choiceOptimizerScope=choice-head-and-value-v1` and refuses to
resume a state produced with the older shared-trunk scope; start a clean output
directory from the desired runtime checkpoint instead.

## Resume and validate

Runtime and trainer checkpoints are atomically replaced. Resume is allowed
only when the supplied `.sdml` hash, progress counters, and immutable training
configuration match the saved trainer state.

```sh
python tools/train_bot_policy.py train \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --output runtime/ml-training/web-v7 --resume \
  [the same training arguments]

python tools/train_bot_policy.py validate \
  --checkpoint runtime/ml-training/web-v7/latest.sdml
```

Validation loads the same checkpoint in Python and TypeScript and compares
fixed-input main action/value/log-probability and masked choice
selection/value/log-probability results.

## Evaluation and diagnostics

`tools/ml_bot/eval-seeds.json` freezes 30 train-distribution and 30 holdout
seeds. Consecutive curriculum scheduling gives every pure/Weld primary exactly
two starting episodes per set. A report is promotion-invalid if a loadout is
missing, has no primary action, or a continuous member never holds primary for
at least two consecutive ten-tick decisions. Comparative claims require both
sets.

```sh
python tools/train_bot_policy.py evaluate \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --seed-set eval_train_dist \
  --report runtime/ml-training/web-v7/eval-train.json

python tools/train_bot_policy.py evaluate \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --seed-set eval_holdout \
  --report runtime/ml-training/web-v7/eval-holdout.json

python tools/train_bot_policy.py probes \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --dataset runtime/ml-training/web-v7/expert-v7.npz \
  --output runtime/ml-training/web-v7/probes.json

python tools/train_bot_policy.py choice-retention \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --dataset runtime/ml-training/web-v7/choice-expert-v7.npz \
  --output runtime/ml-training/web-v7/choice-retention.json

python tools/train_bot_policy.py diagnostics \
  --training-directory runtime/ml-training/web-v7 \
  --output runtime/ml-training/web-v7/dashboard.html
```

Each update records learning metrics plus exact gameplay outcomes: enemy kills
and kinds, waves reached/completed, deaths, potion use, skill picks, gold,
item kinds/counts, health/mana orbs, powerups, XP, reward decomposition, and
action histograms. Learned runs additionally record selected skill IDs,
descriptor families, choice mode, SMDP interval length, spell actions by exact
equipped skill id, exact current pure/Weld action ownership, consecutive
primary-cast runs/ticks, and maximum observed equipped ranks. Evaluation progress
and final reports aggregate those same gameplay counters and chosen-skill IDs,
along with authoritative simulation ticks and policy decisions, so a live run
can be distinguished from an idle or stalled one.
Per-update observation audits, value calibration, and a
spatial replay JSONL are written alongside checkpoints. Render a replay with:

```sh
python tools/train_bot_policy.py replay \
  --source runtime/ml-training/web-v7/replays/update-000001-world-0.jsonl \
  --output runtime/ml-training/web-v7/replay-000001.html
```

Both HTML artifacts are self-contained and read-only.

Screen multiple saved checkpoints on identical seeds before committing to a
full promotion run:

```sh
python tools/train_bot_policy.py arena \
  --checkpoint bootstrap=runtime/ml-training/web-v7/bootstrap-v7.sdml \
  --checkpoint candidate=runtime/ml-training/web-v7/policy-v7-update-000008.sdml \
  --seed-set eval_train_dist --seed-count 4 --maximum-steps 1500 \
  --output runtime/ml-training/web-v7/arena.json
```

An arena with fewer than 30 fully terminated episodes is explicitly marked
`promotionScale=false`. After both 30-seed sets complete for incumbent and
candidate, apply the paired confidence rule:

The promotion reader accepts version-5 or version-6 reports only for the
incumbent slot so deployed and all-primary v6 checkpoints can be compared
during the strict v7 cutover. Candidate reports must be version 7. This is
evaluation-only lineage support; the v7 runtime and checkpoint codec still
reject every legacy artifact.

```sh
python tools/train_bot_policy.py promote \
  --incumbent-train eval-bootstrap-train.json \
  --candidate-train eval-candidate-train.json \
  --incumbent-holdout eval-bootstrap-holdout.json \
  --candidate-holdout eval-candidate-holdout.json \
  --output promotion.json
```

Finally, write one compact campaign receipt containing cumulative gameplay,
episode, KL, clamp, checkpoint-size, and SHA-256 evidence:

```sh
python tools/train_bot_policy.py summarize \
  --training-directory runtime/ml-training/web-v7 \
  --checkpoint runtime/ml-training/web-v7/latest.sdml \
  --output runtime/ml-training/web-v7/campaign-report.json
```
